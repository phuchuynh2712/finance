### Decisions made while writing these tasks

The plan left these implementation details open; they are settled here and reflected back into the plan, research and contracts.

1. **The recompute leaves `updated_at` alone** (a derived value is not a change to push), and the record flows append only the transaction's outbox entry: no item row is pushed for a balance any more.
2. **Item payloads drop `balance`** (the server derives it) and never carry `balance_base` or `server_balance`.
3. **The v8 migration adds columns idempotently** (`PRAGMA table_info`) because older blocks of the same upgrade pass create or recreate tables from the *current* definition, and the v5 test fixture has no `sync_outbox` table; the v6 `TableMigration` gets `newColumns`.
4. **A push response is applied unconditionally** unless a later outbox entry for the same row is still waiting (research Decision 6). Root cause: a local write carries the device's clock as `updated_at`, the server issues its own, and the strictly-newer check ignores the server's row when the device clock runs fast, so "delete wins" and the normalised reversal would never reach the device that acted. This is fixed in the shared worker, in PR 1, not worked around in the new code.
5. **A refused push is repaired locally**: a refused *insert* is removed locally (the server never had it); a refused *update* is replaced by the server's current row unconditionally. Refusals are durable (they stay on their outbox row until their notice is shown, then that row is deleted); overrides and mismatches are live (in memory).
6. **The notices holder, its provider and its host are shared code in PR 1** (`core/sync`, `core/widgets`), because the reconciliation needs them; the domain repository carries no refusal API, and the host reads the holder directly. PR 3 adds the refusal and override reasons to the same host.
7. **Reconciliation (constitution, Offline-First, FR-018)** is built, not waived: a local-only `server_balance` column, a `ReconciliationMonitor` that needs a difference twice, at least 10 seconds apart, then one full `resync`, then one notice, never an overwrite (research Decision 10). Amending the constitution instead was not chosen: that is the owner's decision.
8. **Two pull-time guards mirror the server**: a remote reversal arriving while a different, unsynced local reversal of the same original exists removes the local one (otherwise the local unique index would stall the whole pull); a remote delete of an original also soft-deletes the live local reversals of it (otherwise the local balance is wrong until the local reversal's push is refused).
9. **Pushing is prompt** (SC-004: 10 seconds): the worker drains right after a correction commits and when the Realtime channel reports ready, not only on its 30-second timer.
10. **Small contract refinements**: denials `windowStillOpen` and `notEditable` are added; the amount field of the edit dialog is a digits-only `TextField` (the recording screen's keypad is private to that screen) and the dialog warns, without blocking, when an item would go negative; `correctionSheetNoActionPastWindow` is dropped (a past-window original always offers Reverse); the confirmation lives in its own file; the outbox append and the transaction payload are extracted into one shared `LedgerWrites` helper.
11. **Delete is event-aware from PR 2**: FR-005 forbids deleting one entry of an income alone, so the row selection that finds an income event ships with the first delete; US4 (PR 3) pins events end to end, and `reverse` reuses the same selection.

## Phase 2: Foundational — derived balances, reconciliation and the server ledger (PR 1)

**Purpose**: Make an item's balance a function of its transactions on the device and on the server, make the device reconcile that figure against the server's, and make every push response reach the device, with no visible change. Every later story depends on it: without it a correction cannot be applied exactly once on several devices (research Decisions 1, 6 and 10).

**⚠️ CRITICAL**: No user story work can begin until this phase is complete. Its acceptance tests are SC-006 (an account that never uses the new actions sees zero differences) and SC-008 (a persisting difference is reported, a vanishing one is not).
