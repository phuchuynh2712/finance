# Research: App Rename and Centralized Error Mapping

## Decision 1: Error mapper is a pure function taking `AppLocalizations`, not a `BuildContext`-bound class

**Decision**: `core/error/error_mapper.dart` exposes a top-level function `String mapErrorToMessage(Object error, AppLocalizations l10n)` — pure Dart, no Flutter widget dependency beyond the already-Dart-only `AppLocalizations` generated class.

**Rationale**: Confirmed via direct code reading that 4 of the 7 call sites are Riverpod `StateNotifier`s (`IncomeFormController`, `ExpenseFormController`, `ScanFormController`, `ExpenseControlFormController`) with no `BuildContext` available inside their `catch` blocks. The existing, already-correct pattern in this codebase is: the controller stores the **raw** exception into state (`writeErrorDetail`/`errorMessage`), and the **widget** (which has `BuildContext` via `ref.listen`) is what calls `l10n.xxx(...)` to localize it at display time. This feature must not violate the `domain`/`data` layer's Flutter-independence (Constitution: `domain/` and `data/` MUST have zero Flutter dependency) — but a `StateNotifier` in `presentation/` calling a `core/error/` function that itself takes `AppLocalizations` (not `BuildContext`) is consistent with the rest of the app's boundary rules, since `AppLocalizations` is already the sanctioned way features consume strings (per Constitution's `l10n/` rule), and the 3 non-`StateNotifier` screens (`sign_in_screen.dart`, `sign_up_screen.dart`, `reset_password_screen.dart`) already have `BuildContext`/`l10n` in scope at their catch site so calling the same function inline works identically there.

**Alternatives considered**:
- *A `BuildContext`-first API (`String mapError(BuildContext context, Object error)`)*: rejected — would force every `StateNotifier` call site to thread a `BuildContext` into domain-adjacent state classes, which none of them do today and which risks a stale-context bug if the widget unmounts before the async catch runs (a known Flutter footgun already avoided elsewhere in this codebase via `if (!mounted) return;` guards).
- *A static/global singleton `AppLocalizations` accessor bypassing `BuildContext` entirely*: rejected — no such accessor exists in this codebase (confirmed: `AppLocalizations.of(BuildContext)` is the only access point), and introducing one would be a larger architectural change than this feature's scope justifies.
- *Leave the raw-error-in-state pattern unchanged and only localize at the very last widget-side call*: this is actually the *chosen* shape — the mapper function is called at the same point `l10n.xxxErrorWriteFailedPrefix(...)` is called today (widget-side for the 4 `StateNotifier`s, inline for the 3 screens), it just replaces what's called there.

## Decision 2: Error categorization is string/type based, not a new enum on the mapper's input

**Decision**: The mapper inspects the caught `Object error` using Dart's `is`/`switch` type-checks (`error is AuthApiException`, `error is AuthWeakPasswordException`, `error is SocketException`, `error is TimeoutException`, `error is PostgrestException`, else generic) and, for `AuthApiException`, compares its `.code` field against literal strings (`'invalid_credentials'`, `'email_exists'`, `'user_already_exists'`, `'weak_password'`, `'over_email_send_rate_limit'`) — not against a `gotrue` `ErrorCode` enum constant.

**Rationale**: Direct inspection of the installed `gotrue: 2.26.0` package confirms `AuthApiException.code` is a plain `String?`, and the `ErrorCode` enum shipped by that package (misnamed in casual conversation as "AuthErrorCode") does **not** contain an `invalidCredentials` member at all — wrong-password/wrong-email failures arrive with `code: 'invalid_credentials'` as a raw string with no corresponding enum constant to reference type-safely. The mapper must therefore compare against the literal string `'invalid_credentials'` for that specific case (matching the existing, already-in-production comparison style used by `sign_up_screen.dart`'s `_mapSignUpError`, which already does `error.code == 'email_exists'`), while it MAY use `ErrorCode.emailExists.code`/`ErrorCode.weakPassword.code`/`ErrorCode.overEmailSendRateLimit.code`/`ErrorCode.userAlreadyExists.code` constants (which DO exist) for the other three FR-007 cases, since those particular constants are genuinely present in the installed package version.

**Critical subtlety — `AuthWeakPasswordException` needs its OWN independent `is` check, not just an `AuthApiException.code` comparison**: direct inspection of `gotrue-2.26.0/lib/src/types/auth_exception.dart` confirms `class AuthWeakPasswordException extends AuthException` — it extends the BASE `AuthException` class directly, NOT `AuthApiException`. A Supabase weak-password rejection can therefore arrive as either (a) a plain `AuthApiException` whose `.code` happens to equal `ErrorCode.weakPassword.code`, or (b) a real `AuthWeakPasswordException` instance (which also carries a `.reasons` list of specific violated rules, unused by this feature). Since Dart's `is` check is exact-type/subtype based, a mapper that only checks `error is AuthApiException && error.code == ErrorCode.weakPassword.code` will silently NEVER match case (b) and fall through to the generic fallback instead — this is a real, easy-to-miss correctness bug (previously shipped once during this feature's own task-generation process and caught by `/speckit-analyze`), not a hypothetical. The mapper's weak-password handling MUST therefore be two independent match arms — `error is AuthApiException && error.code == ErrorCode.weakPassword.code` OR `error is AuthWeakPasswordException` — both producing the identical `errorMapperWeakPassword` message, per data-model.md's Error Category table and contracts/error_mapper.md's behavioral contract table.

**Alternatives considered**:
- *Wait for/depend on a future package version that adds `ErrorCode.invalidCredentials`*: rejected — out of this feature's control and scope; the pinned version (`supabase_flutter: ^2.8.0`, resolved 2.16.0) is what ships today.
- *Match on `statusCode == '400'` instead of `code`*: rejected as the primary signal — `400` is also returned for other malformed-request cases, not just bad credentials, so it's a weaker signal than the `code` string which Supabase's Auth API does reliably set to `'invalid_credentials'` for this specific case (confirmed by this codebase's own existing test fixture at `test/widget/features/account/sign_in_screen_test.dart`, which already constructs `AuthApiException('Invalid login credentials', code: 'invalid_credentials')` to simulate this exact failure).
- *Treat `AuthWeakPasswordException` as just another `AuthApiException` subtype check without calling out the distinction explicitly*: rejected — this is exactly the phrasing that caused the original bug; the distinction is called out explicitly here specifically so it can't be silently lost again in a future edit.

## Decision 3: Network/connectivity detection matches on `SocketException`, `TimeoutException`, and gotrue's own `AuthRetryableFetchException`

**Decision**: The mapper treats `error is SocketException` (from `dart:io`), `error is TimeoutException` (from `dart:async`), and `error is AuthRetryableFetchException` (from `gotrue`) as the "couldn't reach the server" category (FR-008), producing the same network-failure friendly message for all three.

**Rationale**: This project has no `dio` dependency and no `connectivity_plus` package — the entire Supabase stack (`gotrue`, `postgrest`, `supabase`, `supabase_flutter`) runs on `package:http`, which surfaces raw `SocketException`/`TimeoutException` from the platform socket layer when a request cannot reach the server at all. `gotrue` additionally wraps some network-retriable failures in its own `AuthRetryableFetchException` type, which this codebase's own existing test suite (`sign_up_screen_test.dart:292`) already uses as its stand-in for "network error," confirming it's the type actually reachable from an Auth call's `catch` block in this stack. No new connectivity-detection infrastructure (e.g. `connectivity_plus`, a pre-flight reachability check) is built — this feature only classifies exceptions that already occur naturally when a call fails due to connectivity, per the Assumptions section of spec.md.

**Alternatives considered**:
- *Add `connectivity_plus` for proactive "are we online" checks before attempting a save*: rejected — out of scope (spec.md Assumptions explicitly says no new network-reachability infrastructure), and would change UX flow (pre-flight blocking) rather than just improving the message shown after a failure already occurred.
- *Rely only on `PostgrestException`/`AuthException` and treat everything else as generic fallback*: rejected — would misclassify the single most common real-world failure (no internet) as a generic "something went wrong" instead of the more actionable "can't reach the server," which FR-008 explicitly requires as a distinct category.

## Decision 4: One shared ARB message set, added to both `app_vi.arb` and `app_en.arb`, following the existing flat-key/no-`@key`-metadata convention

**Decision**: New keys are added directly to `lib/core/l10n/app_vi.arb` and `app_en.arb` as flat `"key": "value"` entries (no `@key` metadata blocks, matching 100% of existing entries in both files), named with an `errorMapper`-prefixed camelCase scheme: `errorMapperInvalidCredentials`, `errorMapperEmailExists` (reuses existing `signUpDuplicateEmailError` text/intent — see Decision 5), `errorMapperWeakPassword`, `errorMapperRateLimited`, `errorMapperNetworkFailure`, `errorMapperGeneric`.

**Rationale**: Every existing ARB entry in this codebase is a flat key with no metadata block — introducing `@key` descriptions here would be inconsistent with 100% of the existing file content, not a genuine improvement. The `errorMapper`-prefix (rather than reusing a screen-name prefix like `signIn*`) reflects that these strings are now owned by a cross-feature shared mechanism, not any single screen — consistent with the Constitution's `core/` rule that shared strings still route through the one `l10n/` mechanism, just with naming that signals shared ownership instead of a single screen's ownership.

**Alternatives considered**:
- *Reuse `signInError`/`signUpError`/etc. per-screen prefixed keys for the new specific messages*: rejected — these categories (invalid credentials, weak password, etc.) are not screen-specific; reusing a screen-prefixed name for a cross-cutting message would be misleading to future readers of the ARB file.
- *One single generic key for everything, differentiated only by a runtime-interpolated category string*: rejected — produces worse UX (can't tailor wording per failure type) and doesn't satisfy FR-007's requirement for *specific* messages per case, only FR-009's fallback case.

## Decision 5: `signUpDuplicateEmailError` stays as-is; the mapper's `email_exists`/`user_already_exists` case reuses its exact text via a shared ARB value, not a code fork

**Decision**: FR-013 (existing sign-up duplicate-email message must keep working) is satisfied by keeping `sign_up_screen.dart`'s `_mapSignUpError` helper's early-return branch for `email_exists`/`user_already_exists` completely untouched, OR by having the mapper produce the *identical* string via `errorMapperEmailExists` reusing `signUpDuplicateEmailError`'s exact current copy — implementation detail decided at plan/tasks time, but the observable string shown to the user for this specific case does not change at all.

**Rationale**: This is a direct regression-avoidance requirement (FR-013, spec.md Edge Cases). `sign_up_screen_test.dart` already has a passing assertion on this exact message; whichever code path is chosen, that test must continue to pass unmodified for this specific scenario. The safest option — least code churn, zero risk of accidentally changing the shown text — is to route the sign-up screen's overall error handling through the new shared mapper (replacing only its *fallback*/`else` branch per FR-011, which lists "sign-up (for its non-duplicate-email fallback path)" as the call site needing the update), while the mapper itself, for the `email_exists`/`user_already_exists` case, returns the same string via a shared key.

**Alternatives considered**:
- *Route 100% of sign-up's error handling (including the duplicate-email case) through the new mapper from scratch, deleting `_mapSignUpError` entirely*: viable and arguably cleaner, but higher regression risk for zero additional user-facing benefit since the string must be byte-identical either way; left as an implementation-time choice, not a spec-level decision, since either satisfies FR-011 + FR-013 equally.

## Decision 6: Rename touches exactly 6 source/generated files plus 13 `specs/` historical files; icon SVGs and platform config files are confirmed clean

**Decision**: The rename (US1/FR-001/FR-004/FR-005) is a documentation-and-string-literal change across a small, fully-enumerated file list — no build configuration, no platform manifest, no icon asset changes.

**Rationale**: Direct source inspection confirms:
- **Live app-facing string**: `signInAppName` key in `lib/core/l10n/app_vi.arb:27` (`"Khai Tâm"`) and `app_en.arb:9` (`"Khai Tam"`) — the generated `app_localizations_vi.dart:30`/`app_localizations_en.dart:30` getters and the doc-comment at `app_localizations.dart:140` are Flutter-generated output that must be regenerated via `flutter gen-l10n` after editing the ARB sources, not hand-edited directly (per this project's own generated-file convention already followed in the prior expense-transaction feature).
- **One non-user-facing doc-comment**: `lib/core/theme/app_theme.dart:6` (`built from the "Khai Tam" brand palette`).
- **13 historical `specs/` files** contain prose mentions across 2 prior features (`20260904-030816-theme-icon-splash`, `20260904-111850-biometric-login`) — spec.md, plan.md, tasks.md, and reference/README.md files, plus one design-spec table cell. Per FR-004, filenames/paths containing the old name in slug form (e.g. any `*-khai-tam*.svg` path segments) are explicitly NOT renamed — only prose content inside file bodies changes.
- **Icon SVG source files** (`assets/icon/appicon*.svg`) contain `aria-label="Khai Tam..."` metadata but are explicitly excluded from this rename per FR-002/user instruction — confirmed present but intentionally left untouched.
- **Android (`AndroidManifest.xml`, `build.gradle.kts`) and iOS (`Info.plist`, `project.pbxproj`)** already use the generic placeholder `"finance"`/`"Finance"`/`com.finance.finance` — confirmed to contain zero occurrences of "Khai Tâm" in any form, so FR-003 ("MUST NOT change applicationId/bundle identifier") requires no action, not an exclusion of an existing occurrence.

**Alternatives considered**: N/A — this decision is a direct inventory, not a design choice with rejected alternatives.
